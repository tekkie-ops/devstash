# Current Feature: Items List View

## Status

In Progress

## Goals

- Add a dynamic route `/items/[type]` that lists items filtered by that type (e.g. `/items/snippets`, `/items/notes`)
- Fetch items by type for the current (demo) user, following the existing `src/lib/db/*` query pattern
- Render a responsive grid of `ItemCard` components — single column on small screens, two columns at `md` and up
- Each card shows a left border colored by its item type
- Match existing codebase conventions (async server components, Prisma-direct queries, `ItemSummary`-style shapes, type label ↔ route slug mapping)

## Notes

- Spec: @context/features/item-list-view-spec.md
- The sidebar Types nav already links to `/items/[label]` (pluralized slug), but the route does not exist yet — this feature creates it.
- Existing dashboard item rendering (`ItemRow.tsx`, `src/lib/db/items.ts`, `ItemSummary`) is the reference; spec calls for a new card component (`ItemCard`) in a grid rather than reusing the row.
- Type ↔ slug conversion already exists as `toLabel` duplicated in `collections.ts` / `items.ts` — reuse/consolidate rather than add a third copy.
- Scope is display-only; no create/edit drawer (separate future feature).

- 2026-09-06: Completed Forgot Password (`771a009`). Built `POST /api/auth/resend-verification` from scratch (IP+email keyed) since the spec assumed it already existed — it didn't, a known gap left by the Email Verification feature (`66e4cdc`) — mirroring `forgot-password`'s always-`{ success: true }` pattern so it never leaks account existence or verification state; `SignInForm.tsx` now offers a "Resend email" action on the `email_not_verified` toast, wired to it. The key design decision was where login rate limiting lives: not at `/api/auth/callback/credentials` (NextAuth's internal route), since the app's own sign-in never calls that route over HTTP — `SignInForm` submits to the `signInWithCredentials` Server Action, which calls `signIn()` in-process — so the IP+email check (5/15min) lives in that action instead, using `headers()` from `next/headers`, and surfaces failures through the same `{ success, error }` toast pattern as its other errors rather than a literal 429/`Retry-After` (that HTTP semantic doesn't apply to a Server Action). One pre-existing bug surfaced and fixed during review: `ForgotPasswordForm.tsx` was discarding the response body on any non-2xx status and showing a generic "Something went wrong" instead of the real message — harmless before this feature since `forgot-password` never returned a specific error, but it would have swallowed the new rate-limit message; changed to parse `body.error` like `RegisterForm`/`ResetPasswordForm` already do. Verified via curl against the dev server with no Upstash credentials configured (confirms fail-open): all four routes validate and respond correctly, invalid-input 400s and bogus-token 400s still behave as before. No Playwright tool was available this session, so the full browser sign-in flow (including the resend-email toast action) wasn't re-verified end-to-end — worth a manual check before relying on it in production. Build and lint passed.
